Before go-live

Production-readiness loose ends

Everything here is a known, deliberate "not yet" — not a bug. Each one was flagged explicitly when its feature was built, as a next step rather than an oversight.

VPS domain & TLSHigh

The VPS is still reachable only over a raw IP on plain HTTP — no domain, no certificate. Deliberately deferred to prove the deployment and sync worked first. Needs a real domain pointed at Caddy before real business/customer data should keep going over this in production.

Real off-site backupsHigh

Litestream's replicate/restore mechanism is built and verified — but only against a local-file stand-in. It isn't pointed at a real S3/B2 bucket yet, so nightly backups aren't actually leaving the box.

SSD swap on the PiHigh

Still running on the original SD card. The setup runbook calls for swapping to a proper SSD before sustained production write load — cheap to do, easy to forget once the system is up and working.

BIR receipt wordingMedium

Official receipt vs. sales invoice wording still needs the client's accountant to confirm. It's a text/settings change on the receipt template, not code — just needs an answer.

New-Pi setup script — untested on real hardwareMedium

Setting up a fresh Pi (hardening, the local server, the sync service) is now scripted end to end instead of run by hand step by step. It's carefully written against the same steps already proven on the current hardware, but hasn't been run start-to-finish on a real board yet — worth a supervised first run before it's relied on for the next branch's setup day.

DigitalOcean Cloud FirewallLow

Only the server's own ufw is active right now. Adding DO's separate Cloud Firewall would be a second layer of defense at effectively no cost.

Multi-branch

In progress

Each location's system now carries its own fixed branch identity, set once at setup rather than per device, with sign-in and reporting locked to it accordingly. What's left mostly needs a second real Pi to finish confirming.

Second Pi — provisioning & real multi-site syncIn progress

A second physical Pi has been ordered. Two real Pis pushing to the same VPS at once has only ever been tested with local stand-ins standing in for each site — never two real boxes syncing simultaneously. That's the one genuinely unconfirmed piece of the multi-branch work.

Branch-routing safeguard — real-world confirmationVerify

A safeguard now keeps each location's device talking only to its own local system for real sales, not the shared cloud server directly. The design is deployed and live, but the exact scenario it's meant to prevent hasn't been re-tested end to end on real hardware yet — worth doing before a second branch is trusted to rely on it.

Device provisioning UILow

A new script now sets up a fresh Pi's branch identity and first admin login in one step, replacing hand-typed setup commands — but it's still a script run from a terminal, not a screen inside the app. Worth a real admin screen once a second branch makes this a recurring task instead of a one-time setup step.

Smaller items

Known gaps, lower priority

Tablet kiosk-lockLow

Staff can currently back out to the home screen or browser mid-shift. Two real options are written up (a quick Settings toggle that needs re-doing after every reboot, or a more durable one-time setup that survives reboots) — neither has actually been turned on on a real tablet yet.

Future phase

Not in this phase

Add-ons, priced and delivered separately from the base system — not part of what's covered above.

Receipt printing (ESC/POS)Future

Built and working — byte-for-byte verified against a simulated printer — but repositioned as a priced add-on rather than base scope, the same track as QR ordering below. Still needs one real hardware test pass (USB transport specifically has none yet) whenever it's actually turned on for a shop.

QR-code table orderingFuture

Customer scans a table code, orders from their phone, and it queues on the cashier's screen. Confirmed architecturally feasible on the current stack — not yet scoped or costed.
